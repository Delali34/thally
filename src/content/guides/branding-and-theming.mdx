## Two places to set your brand

Thally reads branding from two layers:

1. **The admin dashboard** (`/admin/branding`) — an Owner picks the structural theme, brand accent, logo, and favicon and hits **Save**. Changes apply to the live docs site immediately, with **no rebuild or redeploy**. These settings are stored at runtime and layered *on top of* the file defaults below.
2. **Source files** (`src/data/site.ts`, `docs.json`) — the git-committed defaults. They define what a freshly scaffolded site looks like and what renders before any dashboard override exists. Anything not overridden in the dashboard falls back to these.

<Note title="Which should I use?">
Use the **dashboard** for day-to-day changes — theme, brand accent, logo, favicon — with no deploy. Edit the **source files** to set the baseline for a new project, to keep branding in version control, or when you don't run the admin dashboard.
</Note>

The dashboard overrides the structural theme, the **brand accent** (and its focus ring), the logo, and the favicon. The rest of the palette (backgrounds, borders, sidebar tokens) is defined in the source files described below.

### Site backgrounds in Thally Cloud

In your site's **Settings → Branding → Site background**, choose a separate
background for light and dark mode. Use the color picker or enter a hex color.
The preview updates as you edit; the contrast readouts compare your brand color
and the default text palette with the selected background.

The override covers the page canvas, header, sidebar, and cards. It keeps text,
borders, code blocks, and other semantic colors in their existing palette.
Choose a light background for light mode and a dark background for dark mode,
then check readability in both previews.

Choose **Use site default** to remove an override. With no override, the
background comes from `src/data/site.ts`. Managed sites publish these changes
with the next site version. Sites pinned to an older runtime must first upgrade
to a runtime that supports background overrides.

### Reader appearance and background imagery

In **Settings → Branding**, choose the default appearance: **System**, **Light**,
or **Dark**. With the appearance toggle enabled, readers can choose a mode and
their browser remembers it. Hiding the toggle enforces your selection, including
following OS changes for System, even when a reader previously saved another mode.
The default remains System with the toggle visible.

Add one shared background image, or provide separate light and dark images.
The light/shared image is also used in dark mode unless a dark image is set.
A dark image without a shared image appears only in dark mode. Choose **None**,
**Grid**, or **Gradient** for an optional decoration over the background color
and image. Reading surfaces keep a translucent background for legibility.

Self-hosted sites can configure the same options in `docs.json`:

```json
{
  "appearance": { "default": "system", "showToggle": true },
  "background": {
    "image": "public/brand/background-light.png",
    "imageDark": "public/brand/background-dark.png",
    "decoration": "grid"
  }
}
```

Merge these fields into your existing configuration; keep its navigation and
other options. Images may use public-relative PNG, JPG, JPEG, or WebP paths,
or HTTPS image URLs without credentials. Remote images load directly in the
reader's browser. Paths cannot contain traversal segments, and SVG backgrounds
are not supported. Existing sites with no background image or decoration keep
their current appearance. Managed branding overrides matching `docs.json`
fields and takes effect in the next published version; upgrade older runtimes first.

## Site configuration

All site-level settings live in `src/data/site.ts`. Edit this file to set your product name, description, and links. (Name, description, and repo URL can also be overridden live from the dashboard.)

```ts
export const siteConfig: SiteConfig = {
  name: 'Your Product',
  description: 'Documentation for Your Product.',
  repoUrl: 'https://github.com/your-org/your-repo',
  links: [
    { label: 'Get started', href: '/quickstart' },
    { label: 'Support', href: 'https://github.com/your-org/your-repo/issues' },
    { label: 'GitHub', href: 'https://github.com/your-org/your-repo' },
    { label: 'Changelog', href: '/changelog' },
  ],
  // ...brand config
}
```

## Brand presets

Thally ships with two color presets:

- **`primary`** — green accent (emerald tones)
- **`secondary`** — purple accent (violet tones)

Switch between them by changing the `brandPreset` variable:

```ts
const brandPreset: BrandPresetKey = 'primary'  // or 'secondary'
```

## Brand accent (the color picker)

The fastest way to recolor the site is the **dashboard**: under **Branding → Brand accent**, an Owner picks the accent with a color wheel, a set of presets, or by typing a hex/RGB value — for both light and dark mode. A live preview updates as you drag, and **Save** applies it to the running site with no rebuild. The accent drives links, active nav/sidebar states, buttons, and the focus ring; if you set only the light accent, Thally derives a sensible dark-mode shade automatically.

This overrides the accent and focus ring. The rest of the palette—backgrounds,
borders, and sidebar tokens—comes from the source-file presets below. Use the
dashboard for a live adjustment and the files as the versioned baseline.

Card and tile icons are neutral by default. To color every content icon with
the current light or dark brand accent, add this to `docs.json`:

```json
"appearance": {
  "contentIcons": "accent"
}
```

Choosing `"accent"` also gives cards and tiles a restrained accent-aware
border that deepens slightly on hover. Use `iconColor="accent"` or
`iconColor="neutral"` on an individual `<Card>` or `<Tile>` when one item needs
to override the site-wide choice — the border treatment follows the same
per-card override. Accent icons and card chrome use the same live token as
links and controls, so changing the owner-selected brand accent updates them
automatically, in both themes and every locale.

### Icon library

Icon names in cards, accordions, and prompts resolve through one library for
the whole site. Lucide is the default; sites written for Font Awesome or Tabler
names keep them by selecting that library:

```json
"icons": {
  "library": "fontawesome"
}
```

Brand marks such as `python` or `github` render inline under every library.
See [Icons](/components/icons) for the full behaviour and the list of bundled
names.

## Custom colors

To define your own palette, edit the `brandPresets` object in `site.ts`. Each preset has `light` and `dark` variants with these tokens:

| Token | Purpose |
| --- | --- |
| `background` | Page background |
| `card` | One-step elevated card and popover surface (optional) |
| `foreground` | Primary text color |
| `muted` | Subtle background and hover states |
| `mutedForeground` | Secondary text color (optional) |
| `border` | Border color |
| `accent` | Primary brand color (links, active states) |
| `accentForeground` | Text on accent backgrounds |
| `accent2` | Secondary accent for charts and restrained emphasis (optional) |
| `accent2Foreground` | Text on secondary-accent backgrounds (optional) |
| `input` | Form control surface (optional) |
| `sidebar` | Sidebar surface (optional) |
| `ring` | Focus ring color |
| `sidebarActiveBg` | Active sidebar item background |
| `sidebarActiveText` | Active sidebar item text |

Most colors are hex values (e.g. `#10B981`) which are auto-converted to HSL. Optional tokens fall back to their nearest core surface, so existing palettes remain valid. The sidebar state tokens (`sidebarActiveBg`, `sidebarActiveText`) may also use raw HSL strings with opacity (e.g. `'152 60% 88% / 0.55'`) for translucent effects.

## Dark mode

Dark mode is handled automatically by `next-themes`. Users toggle it with the theme switch in the top bar. Your brand palette defines both light and dark variants, so both themes stay on-brand.

## Logo & favicon (light and dark)

The quickest way to set a logo is the **dashboard**: upload a PNG, JPEG, or WebP (≤150KB) under **Branding → Logo & favicon** and it appears in the header and social cards immediately — no code change.

You can upload **separate assets for light and dark mode** — both a logo and a favicon per mode. The site serves the variant that matches the viewer's theme; if you upload only the light-mode asset, dark mode falls back to it, so a single upload still works. This is how a wordmark that reads on a white header can be swapped for a light-on-dark version at night.

To keep artwork in version control, put your files in `public/` and configure their local paths in `docs.json`:

```json
{
  "navbar": {
    "logo": {
      "light": "/brand/product-logo-light.svg",
      "dark": "/brand/product-logo-dark.svg"
    }
  },
  "favicon": {
    "light": "/brand/product-icon-light.svg",
    "dark": "/brand/product-icon-dark.svg"
  }
}
```

For example, `/brand/product-logo-light.svg` refers to `public/brand/product-logo-light.svg`. Use local files rather than external URLs. Omit `dark` to reuse the light asset in dark mode. You do not need to edit runtime components or replace Thally's bundled default files.

Managed branding takes precedence over dashboard uploads, which take precedence over these file defaults. The header, admin chrome, and social cards use the logo; the browser tab and documentation assistant use the favicon. Setting `navbar.logo` to `null` keeps the header and social cards text-only without disabling the favicon.

Social cards support PNG, JPEG, WebP, GIF, and self-contained SVG logos. SVGs with scripts, event handlers, or external resources fall back to the bundled mark; keep exported SVGs self-contained. Missing artwork also falls back safely.

## Fonts

The body and heading fonts are set from a `fonts` block in `docs.json` — any Google Font, no code changes:

```json
"fonts": {
  "body": { "family": "Plus Jakarta Sans", "weight": ["400", "500", "600", "700"] },
  "heading": { "family": "Outfit", "weight": ["600", "700"] }
}
```

The defaults are **Inter** (body) and **JetBrains Mono** (code). The monospace font is still configured in `src/app/layout.tsx` via `next/font/google`. See [Custom fonts](/guides/custom-fonts) for the full reference.

## Third-party analytics scripts

Load Google Analytics 4, Google Tag Manager, Plausible, or PostHog from
`docs.json` or `siteConfig.analytics`. Thally's root layout renders each
configured provider once, so you do not need to edit the layout.

The `docs.json` form uses Mintlify's `integrations` shape, so a migrated site
works unchanged:

```json
"integrations": {
  "ga4": { "measurementId": "G-XXXXXXXXXX" },
  "gtm": { "tagId": "GTM-XXXXXXX" },
  "plausible": { "domain": "docs.yourproduct.com", "server": "plausible.yourproduct.com" },
  "posthog": { "apiKey": "phc_...", "apiHost": "https://us.i.posthog.com", "sessionRecording": true }
}
```

`plausible.server` is only for a self-hosted instance (hostname, no `https://`).
`posthog.apiHost` defaults to `https://us.i.posthog.com`, and
`sessionRecording: false` disables recordings while keeping analytics; a
value that is not `true` or `false` also disables them. PostHog page views are
tracked on every client-side navigation.

`analytics.enabled: false` only controls Thally's first-party analytics. It does
not disable `integrations`: remove a provider from `integrations` to stop it.
Do not enable both `ga4` and `gtm` if the GTM container already contains a GA4
tag, or page views are counted twice.

The code form in `src/data/site.ts` keeps working:

```ts
export const siteConfig: SiteConfig = {
  // ...
  analytics: {
    googleAnalyticsId: 'G-XXXXXXXXXX',
    // or
    plausibleDomain: 'docs.yourproduct.com',
    plausibleScriptUrl: 'https://plausible.io/js/script.js',
    // or
    posthogKey: 'phc_...',
    posthogHost: 'https://us.i.posthog.com',
  },
}
```

Both can be used together. Each provider is resolved independently:
`siteConfig.analytics` wins for a provider it sets, and `docs.json` fills the
providers it does not. Fields are never mixed between the two sources for one
provider. `siteConfig.analytics` is your own code, so its values are used as
written. Google Tag Manager is configured in `docs.json` only.

`docs.json` values can be edited outside code review, so they are validated
before they are placed in a script. An invalid value skips that provider with a
console warning (the value itself is never logged):

| Provider | Accepted |
| --- | --- |
| GA4 | `G-` followed by 4-20 uppercase letters or digits (Universal Analytics `UA-` IDs are unsupported) |
| GTM | `GTM-` followed by 4-12 uppercase letters or digits |
| PostHog | `phc_` project key; `apiHost` an `https://` origin, optionally with a path such as a reverse proxy, without credentials, query, fragment, or `//`; public hostnames only (no IP addresses or `localhost`) |
| Plausible | One or more comma-separated hostnames; `server` a public hostname with an optional port from 1 to 65535 (a pasted `https://` origin is accepted) |

Leave both unset when you do not want third-party scripts. These settings load
the provider SDKs; they do not replace provider-specific single-page
navigation, custom-event, privacy, or consent configuration. Thally sets no
Content-Security-Policy, so no extra allow-list is needed; if you add one, allow
only the hosts of the providers you enable.

## Version switcher

If your docs have multiple versions, add a `versions` array to `siteConfig`. A dropdown appears in the top bar automatically.

```ts
export const siteConfig: SiteConfig = {
  // ...
  versions: [
    { label: 'v2.0', href: '/', current: true },
    { label: 'v1.0', href: 'https://v1.docs.yourproduct.com' },
  ],
}
```

- **`label`** — text shown in the dropdown
- **`href`** — URL for that version (`/` for the current site, or a full URL for older versions)
- **`current`** — marks the active version (exactly one should be `true`)

The switcher is hidden when fewer than two versions are defined.

## Edit on GitHub

When `repoUrl` in `siteConfig` points to a real GitHub repository, every doc page shows "Edit this page" and "Report an issue" links in the page-actions rail (beside the table of contents, or below the article on centered and wide layouts). The edit link opens the MDX source file on the `main` branch; the issue link opens a pre-titled GitHub issue.

```ts
export const siteConfig: SiteConfig = {
  repoUrl: 'https://github.com/your-org/your-docs',
  // ...
}
```

## Changelog RSS feed

Thally serves an RSS feed at `/changelog/rss.xml`. Users can subscribe to it in any RSS reader to get notified of updates. The feed entries are defined in `src/app/changelog/rss.xml/route.ts`.

## Page feedback

The "Was this page helpful?" widget is shown at the bottom of every doc page by default. To configure where feedback votes are sent, add a `feedback` block to `docs.json`:

```json
"feedback": {
  "thumbsRating": true,
  "endpoint": "/api/feedback"
}
```

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `endpoint` | `string` | `/api/feedback` | URL that receives rating and written follow-up POSTs |
| `thumbsRating` | `boolean` | `true` | Show or hide the widget |

Ratings send `{ page, vote, url }`. When written feedback is enabled through a linked Thally Cloud site, an optional note after a "No" rating sends `{ page, vote: "no", message, followUp: true, url }`. Treat `followUp: true` as context for the original rating, not another vote.

The built-in `/api/feedback` route forwards feedback to the configured analytics service and safely no-ops when none is connected. Replace it with your own storage logic in `src/app/api/feedback/route.ts` to write to a database, forward to Slack, or send to another analytics tool.

## Structural themes

Structural themes control the shape and density of the UI — border radius, sidebar active item style, and navigation tab appearance. They are independent of brand colors, so any color preset works with any structural theme.

Set the baseline theme in `docs.json` (or switch it live from the dashboard under **Branding → Structural theme**, no rebuild):

```json
{
  "theme": "maple"
}
```

| Theme | Character | Border radius | Sidebar active | Nav tabs |
| --- | --- | --- | --- | --- |
| `default` | Balanced | Medium (1 rem) | Left indicator + tinted background | Pill with underline accent |
| `maple` | Warm, rounded | Large (1.25–2 rem) | Tinted background pill only | Full-width pill, no underline |
| `sharp` | Technical, precise | Tight (0.25 rem) | Left indicator only, no background | Flat tabs, underline accent |
| `minimal` | Content-first | None (0) | Text color change only | Text tabs, underline accent |

<Tip>
Structural themes and brand colors are orthogonal. You can use the `maple` theme with either the `primary` (green) or `secondary` (purple) brand preset.
</Tip>

## Brand colors and page menu in `docs.json`

`docs.json` can set brand colors without editing `site.ts`:

```json
"colors": {
  "light": { "primary": "#16a34a", "accent": "#16a34a" },
  "dark": { "primary": "#4ade80", "accent": "#4ade80" }
}
```

Use six-digit hex values. `primary` fills buttons; `accent` colors links and highlights.

`contextual.options` sets the entries of the page menu, in display order. Supported entries are `copy`, `view`, `chatgpt`, `claude` and `perplexity`:

```json
"contextual": { "options": ["copy", "view", "chatgpt"] }
```
