## Adding your spec

Place your OpenAPI 3.x spec file in the project root as `openapi.yaml` (or `openapi.json`). Then configure it in `docs.json`:

```json
{
  "tab": "API Reference",
  "api": {
    "source": "openapi.yaml",
    "tagsOrder": ["Users", "Orders", "Products"],
    "defaultGroup": "General"
  }
}
```

The API Reference tab will auto-generate a page for every operation in your spec.

## Configuration options

| Field | Required | Description |
| --- | --- | --- |
| `source` | Yes | Path to your OpenAPI spec file, relative to the project root. |
| `navigation` | No | Set to `false` when authored MDX pages provide API navigation. Defaults to `true`. |
| `groups` | No | Lists the sidebar groups of this tab's operations yourself, replacing the tag groups (see [Authored navigation groups](#authored-navigation-groups)). |
| `tagsOrder` | No | Controls the order tags appear in the sidebar. Unlisted tags appear after. |
| `defaultGroup` | No | Group name for operations without tags. Defaults to `"Endpoints"`. |
| `webhookGroup` | No | Group name for OpenAPI webhook operations. Defaults to `"Webhooks"`. |
| `overrides` | No | Per-operation customizations (see below). |

## Operation overrides

You can customize how individual operations appear in the sidebar and docs:

```json
{
  "api": {
    "source": "openapi.yaml",
    "overrides": {
      "GET /users": {
        "title": "List users",
        "description": "Fetch all users with pagination.",
        "badge": "Stable"
      },
      "DELETE /users/{id}": {
        "title": "Delete user",
        "badge": "Destructive"
      }
    }
  }
}
```

The key format is `METHOD /path` — matching the `method` and `path` from your OpenAPI spec.

Available override fields:

- **`title`** — custom sidebar and page title
- **`description`** — custom description shown below the title
- **`badge`** — a label displayed next to the operation title
- **`group`** — move the operation to a different sidebar group
- **`slug`** — replace the generated URL segments with a string array
- **`hidden`** — keep the operation out of generated navigation and out of the published `/openapi.json` and `/openapi.yaml`

## Hide or exclude operations

Set `x-hidden: true` or `x-excluded: true` in the spec, or use the `hidden` override above, to keep an operation out of the reference. Hidden and excluded operations are also removed from the published `/openapi.json` and `/openapi.yaml`, together with schemas only they used.

The extensions can sit on an operation, on a path item, or on a `paths` entry next to its `$ref`. A `$ref` path item shared by several paths is never edited: `x-hidden` or an override on one path only hides that path, and the shared item stays for the others. An `x-excluded` flag anywhere in a shared item applies to every path that uses it. A `$ref` that cannot be followed (another file, a missing target, a cycle) is left as written unless the entry itself carries a flag.

A page whose `openapi:` frontmatter names a hidden or excluded operation is not published. Its address returns 404, and it is left out of navigation, breadcrumbs, previous and next links, search, the sitemap, `llms.txt`, the Markdown pages and the agent and MCP listings. `thally check` and the build warn and name each such page. This follows the same lookup as the page itself: a value with a spec prefix is judged against that spec, and one without a prefix is published if any API tab's spec publishes the operation. An `openapi:` value that matches no operation at all, or that only a remote spec could serve, is not treated this way.

<Warning title="Keep specs out of public/">
Keep spec files outside `public/`, for example in `openapi/`. Everything under `public/` is served as-is, so a spec there stays fully downloadable, hidden operations included. A file named `public/openapi.json` or `public/openapi.yaml` also answers `/openapi.json` or `/openapi.yaml` in place of the filtered specification. `thally check` and the build warn about OpenAPI files under `public/`. Re-running a migration into an existing site does not remove old copies from `public/`; delete them manually.
</Warning>

## Tag ordering

By default, operations are grouped by their OpenAPI `tags`. The `tagsOrder` array controls the sidebar order:

```json
"tagsOrder": ["Authentication", "Users", "Orders"]
```

Tags not listed in `tagsOrder` appear after the listed ones, in the order they first appear in the spec.

## Authored navigation groups

To choose the groups, their order and the operations the sidebar lists, set `groups` on the tab's `api`. It replaces the tag groups of that tab:

```json
{
  "tab": "API reference",
  "api": {
    "source": "openapi.yaml",
    "groups": [
      {
        "group": "Compute",
        "pages": [
          {
            "group": "Projects",
            "pages": ["POST /v2/projects.createProject", "POST /v2/projects.getProject"]
          }
        ]
      },
      { "group": "Keys", "pages": ["POST /v2/keys.createKey", "WEBHOOK POST keyRotated"] }
    ]
  }
}
```

A group has `group`, an optional `icon` (an icon name or an image path; any other value is dropped and the group stays) and `pages`, like a group of a page tab. Every string in `pages` is an operation key, in the same format as `overrides`: `METHOD /path`, or `WEBHOOK METHOD name` for a webhook. The method is case-insensitive and extra spaces are ignored. The path or webhook name must match the spec exactly.

- **Order.** Operations and groups appear in the order you write them, with no alphabetical sort. Top-level groups become sidebar sections and nested groups become collapsible groups. `tagsOrder`, `defaultGroup`, `webhookGroup` and the `group` override no longer affect that tab's sidebar.
- **Operations you do not list** are not in the sidebar. Their pages and URLs still work, and they stay in search, the sitemap and `llms.txt`.
- **Unknown keys.** A key that matches no published operation (a typo, or a hidden or excluded operation) is skipped, and a group left empty disappears. `thally check` warns about each such key. A key listed twice in one tab appears once, at its first position.
- **Entries that are not valid.** An entry that is not a group with a `pages` list, a `pages` item that is neither an operation key nor such a group, and a group nested more than 32 levels deep are all skipped. `thally check` warns once per tab for each of the two cases, and once per tab when a group `icon` is not text. If `groups` is not a list, the tab shows the generated navigation instead, and `thally check` says so. `thally check` also covers the tabs of each language under `i18n.navigation`, naming the language.
- **`navigation: false` wins.** With it, Thally generates no API navigation at all and `groups` is not used.

## Try It panel

Every API operation page includes a **Try It** button that opens an interactive request panel. It:

- Prefills parameters from the OpenAPI schema
- Sends requests through a server-side proxy to avoid CORS issues
- Displays the response with status code, headers, and body
- Generates a cURL command you can copy

Try It is ready when the specification provides at least one server URL. Add
authentication placeholders only when your API requires them; readers can
enter their own credentials before sending a request.

## Pointing a page at one operation

A page can render a single operation from your spec with `openapi` frontmatter:

```yaml
---
openapi: "POST /things"
---
```

When a site has several specs, prefix the spec file (or URL) exactly as it is
configured in `docs.json`; a leading `/` or `./`, quotes, and a name with spaces
all work, and the file name alone is enough:

```yaml
openapi: "openapi-b.yaml GET /widgets/{id}"
openapi: "/specs/openapi-b.yaml GET /widgets/{id}"
openapi: "openapi-a.json webhook orderUpdated"
```

Without a prefix, the default (first) spec is searched first, then the others in
`docs.json` order. If only later specs match, the first is used and a warning
names the ambiguity; add the prefix to choose. An unknown spec or operation
gives a 404. If a page also sets `api`, `openapi` wins.

## Hand-written API pages

A page without a spec can still get an endpoint header and a Try It panel. Set
`api` to `METHOD` plus a full URL or a path:

```yaml
---
title: Create user
api: "POST https://api.example.com/users/{id}"
authMethod: bearer   # optional: bearer | basic | key | none
---

<ParamField path="id" type="string" default="42" required />
<ParamField query="verbose" type="boolean" />
<ParamField header="X-Trace" type="string" />
<ParamField body="user.name" type="string" required />
```

- A full URL in `api` wins. A path (`api: "GET /status"`) is added to the
  server from `docs.json`. Without either, the page shows the header and the
  playground is disabled with a message.
- The playground fields come from the page's `ParamField` elements
  (`path`, `query`, `header`, `body`; `default` becomes the prefilled value).
  Dotted body names (`user.name`) build nested JSON. Each `{name}` in the path
  is an input even without a `ParamField`. A query string in `api` is prefilled.
- Invalid `api` values (unknown method, non-string, missing path) are ignored
  with a build/server log warning and the page renders as normal MDX.

```json
"api": {
  "mdx": {
    "server": "https://api.example.com",
    "auth": { "method": "bearer" }
  }
}
```

`api.mdx.server` is one URL or a list (readers get a selector). `api.mdx.auth`
takes `method` `bearer`, `basic` or `key` (`key` needs `name`, the header
name) and prefills that header. Only absolute `http(s)` URLs without
credentials are accepted.

The Try It relay only forwards to the server the page itself declares (from its
`api` frontmatter or `docs.json`); it re-reads the page on the server and never
trusts a URL from the browser. Private, loopback and metadata addresses stay
blocked.

## Replace the example spec

The template ships with a JSONPlaceholder specification so you can test the
generated pages without credentials. To use your own API:

1. Replace `openapi.yaml` with your spec
2. Update the `tagsOrder` in `docs.json` to match your tags
3. Add any `overrides` you want
4. Run `npm run dev` to see the result

## Verify the generated reference

Confirm the expected tags and operations appear, open at least one endpoint,
and compare its parameters and schemas with the source specification. Then run:

```bash
npx thally check
npm run build
```

## Playground settings in `docs.json`

```json
"api": { "playground": { "display": "interactive" }, "specLink": true },
"apiPlayground": { "timeoutMs": 60000 }
```

- `api.playground.display` is `"interactive"` (default, shows Try it), `"simple"` (request samples only) or `"none"` (no playground). `"auth"` is not supported and behaves as `"simple"`. A page can override it with `playground:` frontmatter.
- `api.specLink` controls the "OpenAPI specification" link shown above each generated operation. It defaults to `true`; set `false` to hide the line. The spec alternate link in the page metadata stays.
- `apiPlayground.timeoutMs` is how long the Try it relay waits for your API, in milliseconds. The default is 60000, clamped to 1000 through 120000.
- Try it sends header credentials only. An API key declared in a query string or cookie is not sent from the playground; readers can copy the code sample instead.
